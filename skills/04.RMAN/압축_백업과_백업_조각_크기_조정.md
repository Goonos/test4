```sql
-- 같은 대상을 압축 없이와 압축으로 백업해 크기와 시간을 비교한다.
-- MAXPIECESIZE로 조각 크기를 제한한다.
-- SECTION SIZE로 큰 파일을 나눠 병렬 처리한다.
-- MAXSETSIZE를 잘못 설정했을 때의 실패를 확인한다.
-- 작업 유형 : 백업 최적화(장애 복구 아님)

**사전 조건**
[세션: RMAN (Target + Catalog 동시 접속)]
SHOW COMPRESSION ALGORITHM;
현재 데이터베이스에 설정된 RMAN 압축 알고리즘을 확인합니다. 별도 구매 옵션(ACO) 없이 사용할 수 있는 BASIC 압축이 기본값으로 설정되어 있습니다.

**초기 상태 확인 : 압축 없는 백업**
[세션: RMAN (Target + Catalog 동시 접속)]
BACKUP AS BACKUPSET DATAFILE 1 FORMAT '/fra/backup/hotbackup/nocomp_%U' TAG 'NOCOMP';
비교 대상을 만들기 위해 1번 데이터파일(SYSTEM)을 압축 옵션 없이 일반 백업 세트 형식으로 백업합니다. (알려주신 핫 백업 경로 적용)

[세션: Linux OS Shell]
ls -l /fra/backup/hotbackup/nocomp_*
OS 상에서 압축 없이 백업된 파일의 물리적 크기를 확인합니다.
sqlplus -s / as sysdba <<< \
"SELECT input_type, elapsed_seconds AS secs,
 ROUND(input_bytes/1024/1024) AS in_mb, ROUND(output_bytes/1024/1024) AS out_mb,
 ROUND(compression_ratio,2) AS ratio
 FROM v\$rman_backup_job_details ORDER BY start_time DESC FETCH FIRST 1 ROWS ONLY;"
 
 v$rman_backup_job_details 뷰를 조회하여 방금 수행한 RMAN 작업(세션)의 소요 시간(secs), 입력 데이터 크기(in_mb), 출력 파일 크기(out_mb)를 확인합니다. 압축 옵션을 주지 않았더라도, RMAN의 백업 세트 방식은 데이터파일 내의 빈 블록(사용되지 않은 공간)을 자동으로 건너뛰고 백업하므로 원본 파일 크기보다 작아진 것을 확인할 수 있습니다.

**작업 수행 : 압축 백업**
[세션: RMAN (Target + Catalog 동시 접속)]
BACKUP AS COMPRESSED BACKUPSET DATAFILE 1 FORMAT '/fra/backup/hotbackup/comp_%U' TAG 'COMP';
이번에는 동일한 1번 데이터파일에 대해 RMAN 엔진 압축(COMPRESSED) 옵션을 주어 백업을 수행합니다.

[세션: Linux OS Shell]
ls -l /fra/backup/hotbackup/comp_*
생성된 압축 백업 파일의 크기를 확인합니다. 압축 전보다 용량이 크게 줄어들었음을 알 수 있습니다

sqlplus -s / as sysdba <<< \
"SELECT elapsed_seconds AS secs, ROUND(input_bytes/1024/1024) AS in_mb,
 ROUND(output_bytes/1024/1024) AS out_mb, ROUND(compression_ratio,2) AS ratio
 FROM v\$rman_backup_job_details ORDER BY start_time DESC FETCH FIRST 1 ROWS ONLY;"
뷰 조회를 통해 압축 비율(ratio)과 소요 시간을 확인합니다. 디스크 I/O가 병목인 환경에서는 기록해야 할 파일 크기(I/O량)가 줄어들기 때문에 압축을 하더라도 오히려 백업 소요 시간이 단축될 수 있습니다. (반대로 CPU가 병목인 시스템에서는 압축 연산 부하로 인해 시간이 더 걸릴 수 있습니다.)

**진행 로그 : 조각 크기 제한**
[세션: RMAN (Target + Catalog 동시 접속)]
RUN {
   ALLOCATE CHANNEL c1 DEVICE TYPE DISK
     FORMAT '/fra/backup/hotbackup/piece_%U' MAXPIECESIZE 200M;
   BACKUP DATAFILE 1 TAG 'PIECES';
   RELEASE CHANNEL c1;
}

테이프 백업 장치나 파일 시스템의 단일 파일 크기 제한을 우회하기 위해, 1개의 채널을 할당하고 생성될 백업 피스의 최대 크기를 200MB(MAXPIECESIZE 200M)로 제한하여 백업을 수행합니다.

LIST BACKUP TAG 'PIECES';
결과를 확인해 보면, 백업 세트(Backup Set)는 1개지만 200MB 제한에 걸려 물리적인 백업 피스(Backup Piece) 파일이 4조각으로 분할되어 생성되었음을 알 수 있습니다.

**진행 로그 : 다중 섹션 백업**
[세션: RMAN (Target + Catalog 동시 접속)]
BACKUP SECTION SIZE 200M DATAFILE 1 FORMAT '/fra/backup/hotbackup/sect_%U' TAG 'SECTION';
이번에는 매우 큰 단일 데이터파일을 병렬로 빠르게 백업하기 위해, 파일 자체를 200MB 단위의 논리적 구역(Section)으로 나누어 여러 채널이 동시에 나누어 읽고 쓰게 하는 SECTION SIZE 옵션을 사용해 봅니다. 단, 이전 세션의 MAXPIECESIZE 제한 설정이 세션에 남아있어 기능 충돌로 오류(RMAN-06808)가 발생합니다.

[세션: RMAN (새 세션으로 Target + Catalog 동시 재접속)]
BACKUP SECTION SIZE 200M DATAFILE 1 FORMAT '/fra/backup/hotbackup/sect_%U' TAG 'SECTION';
기존 RMAN 세션을 종료하고 새 세션으로 접속하여 깨끗한 상태에서 다중 섹션 백업 명령을 재실행합니다. 할당된 채널들이 데이터파일의 블록을 200MB 구간별로 번갈아 가며 동시에 스캔 및 백업하는 것을 로그로 확인할 수 있습니다. MAXPIECESIZE는 단일 채널이 결과 파일만 잘게 쪼개는 것이고, SECTION SIZE는 작업 자체를 여러 채널이 분담하여 성능을 높이는 차이가 있습니다.

**오류 발생 → 원인 파악 → 수정**
[세션: RMAN (Target + Catalog 동시 접속)]
CONFIGURE MAXSETSIZE TO 100 M;
이번에는 RMAN 영구 설정으로 '백업 세트' 전체 크기의 상한선을 100MB로 제한해 봅니다.

BACKUP DATAFILE 1;
1번 데이터파일을 백업하려 시도하지만 오류(RMAN-06183)가 발생합니다. 데이터파일 하나의 크기(890MB)가 설정해 놓은 백업 세트 제한 크기(100MB)보다 크기 때문에 논리적으로 백업 세트를 생성할 수 없어 실패하는 것입니다. 백업 파일 크기를 쪼개는 것이 목적이라면 MAXPIECESIZE를 써야 합니다.

CONFIGURE MAXSETSIZE CLEAR;
잘못 설정된 제한값을 CLEAR를 통해 오라클 기본값(UNLIMITED)으로 원상 복구합니다.

SHOW MAXSETSIZE;
제한값이 기본 상태로 잘 풀렸는지 조회합니다.

BACKUP DATAFILE 1 TAG 'AFTER_FIX';
설정을 고친 후 다시 백업을 시도하여 정상적으로 완료되는 것을 확인합니다.
```
