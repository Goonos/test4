## [1] 시나리오 개요

OS 명령(dd)을 통해 데이터파일의 특정 블록을 물리적으로 손상(Corruption)시킨 후 애플리케이션 조회 시 발생하는 오류 양상을 관찰하고 RMAN VALIDATE를 통한 사전 감지 방법과 비교한다. 손상 발생 시 v$database_block_corruption 뷰에 메타데이터가 자동 등록되는 Health Check 메커니즘을 이해하고, dba_extents 뷰를 활용하여 손상된 블록이 속한 데이터베이스 객체를 역추적하여 진단한다. (실제 복구는 16-7 실습에서 연계 수행)

## [2] 사전 조건

[경고] 운영(Production) 데이터베이스 환경에서는 절대 수행하지 않으며, 오직 테스트용 데이터베이스에서만 수행한다. 실습 중 운영 시스템이나 다른 공용 테이블스페이스에 영향을 주지 않도록 격리된 실습 전용 테이블스페이스(tbs16)를 신규 생성하고, 실습 전 정상 상태를 보장하는 베이스 백업을 생성한다.
[oracle@oel7v9 ~]$ sqlplus / as sysdba

-- 실습용으로 사용할 격리된 테이블스페이스 'tbs16'을 생성한다.
SYS@orcl> CREATE TABLESPACE tbs16 DATAFILE '/u03/oradata/ORCL/tbs16_01.dbf' SIZE 60M;

-- 생성된 실습용 테이블스페이스의 물리적 데이터파일 번호(file# 9)를 확인한다.
SYS@orcl> SELECT file#, name FROM v$datafile WHERE name LIKE '%tbs16%';

SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat

-- 실습 전 정상 상태를 보장하는 데이터베이스 베이스 백업을 수행한다.
RMAN> BACKUP DATABASE TAG 'BASE_165' PLUS ARCHIVELOG;

RMAN> EXIT


[3] 초기 상태 확인
실습 전용 테이블스페이스에 테스트용 테이블을 생성하고 500건의 더미 데이터를 삽입 후 데이터파일에 물리적으로 강제 기록(CHECKPOINT)한다. 이후 DBMS_ROWID 패키지를 사용하여 해당 테이블 데이터가 저장된 논리적 블록 번호 범위와 속한 파일 번호를 추출하고, 손상 유발 전 RMAN VALIDATE 명령을 수행하여 해당 데이터파일에 블록 손상이 0건(Status OK)임을 사전에 확인한다.
[oracle@oel7v9 ~]$ sqlplus / as sysdba

-- 실습용 테이블스페이스에 테스트 객체인 'blk165' 테이블을 생성한다.
SYS@orcl> CREATE TABLE hr.blk165(id NUMBER, pad VARCHAR2(2000)) TABLESPACE tbs16;

-- 테스트 테이블에 500건의 더미 데이터를 삽입한다.
SYS@orcl> INSERT INTO hr.blk165 SELECT LEVEL, RPAD('x', 2000, 'x') FROM dual CONNECT BY LEVEL <= 500;

-- 삽입된 데이터를 커밋하여 트랜잭션을 완료한다.
SYS@orcl> COMMIT;

-- 메모리 버퍼 캐시의 더미 데이터를 물리적 디스크(데이터파일)로 강제 기록한다.
SYS@orcl> ALTER SYSTEM CHECKPOINT;

-- DBMS_ROWID를 이용해 데이터가 기록된 최소/최대 블록 번호 및 파일 번호를 추출한다.
SYS@orcl> SELECT MIN(DBMS_ROWID.rowid_block_number(ROWID)) AS min_blk, MAX(DBMS_ROWID.rowid_block_number(ROWID)) AS max_blk, MIN(DBMS_ROWID.rowid_relative_fno(ROWID)) AS file_no FROM hr.blk165;

SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target /

-- 블록 손상 유발 전, RMAN VALIDATE를 통해 9번 파일에 손상이 없음(Status OK)을 확인한다.
RMAN> VALIDATE DATAFILE 9;

RMAN> EXIT

[4] 장애 유발 : dd로 블록 손상
버퍼 캐시 내의 정상 블록 이미지와 파일의 손상된 블록 데이터 간의 불일치를 방지하기 위해 데이터베이스를 우선 종료(Down) 상태로 전환한다. 만일의 사태를 대비하여 OS 레벨에서 원본 데이터파일을 복제해둔 뒤, dd 유틸리티를 사용하여 /dev/zero(0값)를 해당 데이터파일의 특정 블록 영역에 강제로 덮어쓴 후 인스턴스를 재오픈한다.
-- 메모리 내 정상 블록이 디스크에 기록되는 것을 방지하기 위해 인스턴스를 정상 종료한다.
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< "SHUTDOWN IMMEDIATE"

-- 원본 데이터파일이 완전히 파괴될 경우를 대비해 OS 레벨에서 백업 복사본을 생성한다.
[oracle@oel7v9 ~]$ cp -p /u03/oradata/ORCL/tbs16_01.dbf /tmp/tbs16_ok.dbf

-- OS dd 유틸리티로 9번 파일의 142번째 블록부터 3개의 블록에 0(/dev/zero)을 덮어써 물리적 손상을 유발한다. (파일이 잘리지 않도록 conv=notrunc 옵션 필수 적용)
[oracle@oel7v9 ~]$ dd if=/dev/zero of=/u03/oradata/ORCL/tbs16_01.dbf bs=8192 seek=142 count=3 conv=notrunc

-- 블록 손상이 적용된 상태에서 데이터베이스 인스턴스를 기동한다.
[oracle@oel7v9 ~]$ sqlplus -s / as sysdba <<< "STARTUP"

[5] 증상 관찰
버퍼 캐시를 비워 물리적 읽기를 강제한 후 테이블을 조회하면 ORA-01578 (ORACLE data block corrupted) 에러가 발생하며, ORA-26040 에러가 동반되지 않으므로 순수한 물리적 블록 손상임을 인지할 수 있다. Oracle 19c부터는 백그라운드 프로세스가 손상 블록에 접근하는 즉시 Health Check 메커니즘이 작동하여 v$database_block_corruption 뷰에 손상 이력(CORRUPTION_TYPE = 'ALL ZERO')을 자동 등록한다.
[oracle@oel7v9 ~]$ sqlplus / as sysdba

-- 버퍼 캐시를 비워 이후 쿼리 실행 시 손상된 디스크 파일을 직접 읽도록 유도한다.
SYS@orcl> ALTER SYSTEM FLUSH BUFFER_CACHE;

-- 테이블 전체 데이터 조회를 시도하면 손상된 블록을 읽는 시점에 ORA-01578 에러가 발생한다.
SYS@orcl> SELECT COUNT(*) FROM hr.blk165;

-- 조건절을 주어 조회하더라도 읽어야 할 블록 영역이 손상되었다면 동일한 ORA-01578 에러가 발생한다.
SYS@orcl> SELECT COUNT(*) FROM hr.blk165 WHERE id <= 10;

-- 19c부터 자동 등록되는 딕셔너리 뷰를 조회하여 142번 블록부터 3건의 'ALL ZERO' 손상 이력을 확인한다.
SYS@orcl> SELECT * FROM v$database_block_corruption;

[6] 진단
알럿 로그를 확인하면 자동 진단 기능이 새로운 영구 데이터 손상을 감지했음을 보여준다. RMAN VALIDATE를 수행하면 파일 Status가 'FAILED'로 변경되고 'Blocks Failing (Other)' 항목에 손상 건수가 집계된다. 딕셔너리 뷰(dba_extents)를 조회하여 손상된 블록이 소속된 객체를 역추적하면 대상이 테이블(TABLE) 객체임이 식별되므로 추후 RMAN 블록 복구 방식이 적합함을 판단할 수 있다.
-- 알럿 로그 꼬리를 확인하여 자동 진단(Checker run)이 제로 블록 손상 3건을 감지했음을 확인한다.
SYS@orcl> !tail -6 /u01/app/oracle/diag/rdbms/orcl/orcl/trace/alert_orcl.log

SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat

-- RMAN VALIDATE를 실행하여 9번 데이터파일의 Status가 'FAILED'로 떨어지고 'Other' 손상 3건이 발견됨을 교차 검증한다.
RMAN> VALIDATE DATAFILE 9;

RMAN> EXIT

[oracle@oel7v9 ~]$ sqlplus / as sysdba

-- dba_extents 뷰와 손상 블록 번호(142)를 매핑하여 손상된 객체가 'BLK165' 테이블(TABLE)임을 식별해 낸다.
SYS@orcl> SELECT owner, segment_name, segment_type FROM dba_extents WHERE file_id = 9 AND 142 BETWEEN block_id AND block_id + blocks - 1;

[7] 오류 발생 → 원인 파악 → 수정 (백업 관점)
손상된 상태에서 일반 백업을 시도하면 ORA-19566 에러가 발생하며 백업이 중단된다. 부득이하게 백업을 강행해야 할 경우 MAXCORRUPT 파라미터를 사용하여 허용 임계치를 일시적으로 늘려 백업을 수행할 수 있다. 단, 이 백업본 안에는 손상된 블록이 그대로 유지되어 해당 블록을 복구할 수는 없다.

SYS@orcl> EXIT

[oracle@oel7v9 ~]$ rman target / catalog rcatowner@rcat

-- 블록이 손상된 파일의 일반 백업을 시도하면 무결성 검증에 걸려 ORA-19566 에러와 함께 백업이 실패한다.
RMAN> BACKUP DATAFILE 9;

-- SET MAXCORRUPT 임계치를 10으로 올려 손상된 블록 3건을 무시하고 강제로 백업을 수행(WITH_CORRUPT 태그 부여)한다.
RMAN> RUN {
   SET MAXCORRUPT FOR DATAFILE 9 TO 10;
   BACKUP DATAFILE 9 TAG 'WITH_CORRUPT';
}
