-- 데이터파일·리두·컨트롤파일이 모두 사라진 상황을 RMAN으로 복구한다.
-- RECOVER가 마지막 아카이브까지 적용한 뒤 RMAN-06054로 멈추는 것을 확인한다.
-- 이어서 복구 시점을 잘못 잡은 상황을 만들고 인카네이션을 되돌린다.
-- 12장의 전체 손실 복구와 대응시켜 확인한다.
-- 복구 유형 : 불완전 복구(마지막 아카이브까지) + 인카네이션 되돌리기

**사전 조건**
[세션: RMAN (Target + Catalog 동시 접속)]

데이터베이스와 아카이브 로그를 모두 백업합니다. 이번 실습의 조건은 데이터 영역(운영 환경)과 백업/아카이브 영역이 물리적으로 분리되어 있어 데이터만 모두 날아가는 상황입니다.

**초기 상태 확인**
[세션: SQL*Plus (SYSDBA)]

만약의 사태를 대비해 DBID를 메모합니다.

CREATE TABLE hr.rec1510(id NUMBER, memo VARCHAR2(30)) TABLESPACE users;
INSERT INTO hr.rec1510 VALUES (1, 'archived');
COMMIT;
ALTER SYSTEM ARCHIVE LOG CURRENT;
백업 이후의 트랜잭션을 아카이브합니다. 이 데이터는 나중에 무사히 복구되어야 합니다.

SELECT current_scn FROM v$database;
아카이브 직후의 SCN 값을 기록합니다. (나중에 복구 상한선과 비교하기 위함입니다.)

INSERT INTO hr.rec1510 VALUES (2, 'only in current redo');

아카이브되지 않은 최신 온라인 리두 로그(CURRENT)에만 존재하는 데이터를 추가합니다.

SELECT MAX(sequence#) FROM v$archived_log WHERE status = 'A' AND resetlogs_change# = (SELECT resetlogs_change# FROM v$database);

백업본과 아카이브 로그 파일들은 다른 디스크에 안전하게 살아있음을 확인합니다.

오라클을 켜보지만 컨트롤파일이 없으므로 당연히 NOMOUNT에서 멈춥니다.

[세션: Linux OS Shell]
운영 디렉터리를 샅샅이 뒤져봐도 세 종류의 파일이 모두 없음을 눈으로 직접 확인합니다.

**복구 절차 : 오류 발생 → 원인 파악 → 수정**
[세션: RMAN (Target + Catalog 동시 접속)]
RESTORE CONTROLFILE;
(카탈로그 접속 상태이므로) 단 한 줄의 명령어로 컨트롤파일을 모든 운영 경로에 무사히 복원합니다.

ALTER DATABASE MOUNT;
컨트롤파일이 돌아왔으니 인스턴스를 MOUNT로 올립니다.

RESTORE DATABASE;
모든 데이터파일을 제자리로 복원해 냅니다.

RECOVER DATABASE;
리두를 들이부어 동기화를 시도합니다. RMAN은 살아있는 마지막 아카이브 로그(5번)까지 무사히 적용한 후, 온라인 리두 로그(6번)를 찾다가 없으니까 RMAN-06054 (unknown archived log) 에러를 뱉으며 장렬히 전사(멈춤)합니다.
이것은 치명적 오류가 아니라, "내가 가진 로그로는 더 이상 미래로 갈 수 없어! 여기가 도달 가능한 한계야!"라는 복구 완료 신호입니다. (수동 복구 시 UNTIL CANCEL 후 CANCEL을 치는 것과 완벽히 동일한 메커니즘입니다.)

ALTER DATABASE OPEN RESETLOGS;
완전 복구(CURRENT 리두 적용)에 실패했으므로 과거 시점으로 분기하기 위해 RESETLOGS로 오픈합니다.

**검증 1차 : 복구 한계점 확인**
[세션: SQL*Plus (SYSDBA)]
SELECT id, memo FROM hr.rec1510 ORDER BY id;
조회 결과, 아카이브 로그에 안전하게 들어있던 1번 데이터는 복구되었으나, 삭제된 온라인 리두(CURRENT)에만 있었던 2번 데이터는 영구 유실(손실)되었음을 확인합니다.

SELECT resetlogs_change# FROM v$database;
새로 뻗어나간 인카네이션의 시작점(SCN)을 확인해 보면, 장애 직전 아카이브 직후 메모해 두었던 SCN 값과 일치합니다. 딱 아카이브가 존재하는 곳까지만 복구가 진행된 것입니다.

**복구 절차 : 인카네이션 되돌리기 (더 과거로 가기)**
만약 방금 복구한 시점(1번 데이터 직후)보다 더 과거 시점(1번 데이터 입력 이전)으로 되돌아가야 한다면 어떻게 해야 할까요? 이미 RESETLOGS를 쳐서 생애 주기가 바뀌었기 때문에 타임머신을 한 번 더 타야 합니다.

[세션: SQL*Plus (SYSDBA)]
SELECT ORA_ROWSCN FROM hr.rec1510 WHERE id = 1;
1번 데이터가 입력된 시점(SCN)을 확인합니다. 이 시점 직전(과거)으로 돌아갈 것입니다.

[세션: RMAN (Target + Catalog 동시 접속)]
LIST INCARNATION;
현재 인카네이션 번호(예: 5969)와 돌아가려는 SCN이 속한 과거 인카네이션 번호(예: 5696)를 확인합니다.

SHUTDOWN IMMEDIATESTARTUP MOUNT
RUN {
   SET UNTIL SCN 2672395;
   RESTORE DATABASE;
   RECOVER DATABASE;
}
RMAN-20208 (UNTIL CHANGE is before RESETLOGS change) 에러가 뜹니다. 현재 인카네이션(새 세계선)의 시작점보다 더 과거로 가려고 하니 오라클이 타임라인 모순을 지적하는 것입니다.

RESET DATABASE TO INCARNATION 5696;
[핵심] 데이터베이스의 타임라인을 명시적으로 과거의 인카네이션(5696)으로 되돌려버립니다.
RUN {
   SET UNTIL SCN 2672395;
   RESTORE DATABASE;
   RECOVER DATABASE;
}

인카네이션을 롤백하고 다시 명령을 날리면, 무사히 과거 백업과 아카이브를 사용해 지정된 과거 SCN으로 복구(타임머신)를 완수합니다.

ALTER DATABASE OPEN READ ONLY;
데이터를 검증하기 위해 읽기 전용으로 오픈합니다. (이번엔 인카네이션을 되돌린 상태라 컨트롤파일 갱신 우회 없이 바로 열립니다.)

**검증 2차 : 인카네이션 롤백 확인**
[세션: SQL*Plus (SYSDBA)]
SELECT COUNT(*) FROM hr.rec1510;
1번 데이터마저 입력되기 전의 과거 시점(0건)으로 데이터가 완벽히 되돌아갔음을 확인합니다.

[세션: RMAN (Target + Catalog 동시 접속)]
SHUTDOWN IMMEDIATE
STARTUP MOUNT
ALTER DATABASE OPEN RESETLOGS;
원하는 과거 시점이 맞으므로 다시 RESETLOGS로 쳐서 여기서부터 또 다른 새로운 미래(인카네이션)를 시작합니다.

LIST INCARNATION;
리스트를 조회해 보면 방금 버려진 잘못된 인카네이션은 고아(ORPHAN) 상태로 남고, 방금 새로 연 인카네이션이 CURRENT로 활성화됨을 볼 수 있습니다.

BACKUP DATABASE TAG 'AFTER_INCARNATION' PLUS ARCHIVELOG;
시간 선을 뒤틀었으므로 반드시 즉시 전체 백업을 수행하여 새로운 기준점을 세웁니다.
